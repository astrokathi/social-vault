ReelVault Course • Lesson 0001

Architecture Foundations & Reactive SQLite with Drift

Feature-First Clean Architecture, Indexed Schemas, and the iOS Sandbox RelPath Pattern.

1. The Problem: Local-First Media Needs True Relational Integrity

Building a personal offline vault like ReelVault requires more than key-value storage (like SharedPreferences or Hive). We are managing thousands of saved Instagram Reels, Carousels, and Photos organized by Collections, filtered by completion thresholds (e.g. "Hide 100% Watched"), and queried in random or sequence playback orders.

If an app stores 10,000 video records, a simple un-indexed query or linear scan causes frame drops during vertical swipes. Drift compiles typed Dart queries into high-performance C SQLite calls backed by binary B-Trees.

Architectural Invariant

Never store full absolute file paths (e.g., /var/mobile/Containers/Data/Application/<UUID>/...) in SQLite on iOS! Every time iOS updates or restarts an app, that container <UUID> can change. We only store relative paths (e.g., vault_media/C9xLmP2oQ1z/thumb.webp) and prepend getApplicationDocumentsDirectory().path at runtime.

2. System Topology & Clean Architecture Directory Flow

ReelVault adopts Feature-First Clean Architecture. Instead of grouping all models together and all widgets together, every domain feature owns its providers, widgets, and screens:

lib/ ├── core/ <-- Shared themes, URL sanitizer, adaptive layout breakpoints ├── data/ │ ├── database/ <-- Drift SQLite schema, reactive streams & seed records │ └── services/ <-- OS Share intent listener, OpenGraph parser, binary cache └── features/ ├── share_sheet/ <-- Native interceptor & Collection Picker bottom sheet ├── feed/ <-- Endless vertical PageView, Video Player & Carousel slider ├── collections/ <-- 2x2 Mosaic Folder cards & 3-column media grid └── profile/ <-- Storage telemetry, cache cleaner, backup export

3. Drift Schema Deep-Dive: Reactive Queries with Indexing

In lib/data/database/app_database.dart, we defined two core tables with explicit database indexes: 

@DataClassName('VaultMediaEntity')
@TableIndex(name: 'idx_media_shortcode', columns: {#shortcode}, unique: true)
@TableIndex(name: 'idx_media_collection', columns: {#collectionId})
@TableIndex(name: 'idx_media_progress', columns: {#watchProgress})
class VaultMediaItems extends Table { ... }

Why index watchProgress? Because our endless feed query filters items dynamically: 

Stream<List<VaultMediaEntity>> watchFeedQueue({required bool hideCompleted}) {
  final query = select(vaultMediaItems);
  if (hideCompleted) {
    query.where((tbl) => tbl.watchProgress.isSmallerThanValue(0.98));
  }
  query.orderBy([(t) => OrderingTerm(expression: t.createdAt, mode: OrderingMode.desc)]);
  return query.watch(); // Emits new list automatically on any DB write!
}

Calling .watch() creates an active SQLite hook. When the video player reaches 100% and commits a progress update, Drift triggers the stream, and Riverpod's StreamProvider updates the UI seamlessly without messy event buses or manual refreshes.
